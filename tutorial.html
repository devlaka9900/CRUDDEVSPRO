Hard-code a PyQt6 + SQLite CRUD app, one commit at a time

Your first real assignment. No generators, no ORM, no Qt Designer, no copy-paste. You type every line, you understand every line, and by the end you own a small but properly structured desktop application.

Python 3.11+ PyQt6 SQLite (built into Python) Layered architecture 14 git commits About 5–7 hours

Welcome: what you are going to build

You are joining the team as a junior, and my job is to turn you into an engineer people trust with production code. The fastest way I know is to make you build something small completely by hand, so that nothing in it is magic.

The app is a Todo manager for the desktop:

  • Create a task in a dialog (title, description, status, priority, optional due date).
  • Read all tasks in a table, with live search and a status filter.
  • Update a task by double-clicking it.
  • Delete a task, after a confirmation.
  • Everything is validated, saved in a database file, covered by tests, and committed in small honest steps.
Why hard-code?

Frameworks hide the parts that make you a good engineer: where SQL lives, how data flows, how a button click becomes a database write. If you learn those by hand once, every framework you meet later (Django, SQLAlchemy, Qt Designer, web stacks) will make sense, because you will recognise what it is doing for you.

About “mysql lite”

The brief says mysql lite. We are using SQLite: a complete SQL database stored in a single file, shipped inside Python (import sqlite3). There is no server to install or configure. The SQL you learn here (SELECT, INSERT, UPDATE, DELETE) transfers almost unchanged to MySQL and PostgreSQL.

What you will learn

Engineering

  • Layered architecture and import rules
  • Separating data, logic and UI
  • Validation and error handling
  • Small commits with meaningful messages
  • Automated tests with pytest

Technology

  • SQL CRUD with parameterised queries
  • Python dataclasses and context managers
  • Qt widgets, layouts, dialogs
  • Signals and slots
  • Styling with QSS

The ground rules

  1. Type every character yourself. No copy-paste, no AI autocomplete. Your fingers must learn the shapes, and typos teach you to read error messages. (That is also why the code blocks in this guide have no copy button.)
  2. Read the “Why” box before the code. Code without a reason is cargo cult.
  3. Run it after every step. Never start a new step on top of something broken.
  4. One checklist group = one commit, with the exact message I give you. Your git history is part of your work and I will read it.
  5. Stuck for more than 15 minutes? Re-read the step, read the “Common mistakes” list, add a print(), read the last line of the traceback. Then come and ask me, and tell me what you already tried.
  6. Do not redesign my structure until you finish. Improvements belong in the stretch goals.
Careful with old tutorials

Most PyQt examples online are for PyQt5. PyQt6 changed enums to be fully qualified: Qt.AlignmentFlag.AlignLeft instead of Qt.AlignLeft, QMessageBox.StandardButton.Yes instead of QMessageBox.Yes, app.exec() instead of app.exec_(). If you see AttributeError mentioning an enum, this is almost certainly why.

Four ideas you need before typing

1. CRUD is just four SQL verbs

LetterUser actionSQLOur function
CreateClick “+ Add task”INSERT INTO ...task_repo.create()
ReadOpen app, search, filterSELECT ... WHERE ...task_repo.list_all(), get_by_id()
UpdateDouble-click, edit, saveUPDATE ... SET ... WHERE id = ?task_repo.update()
DeleteSelect, click Delete, confirmDELETE FROM ... WHERE id = ?task_repo.delete()

2. A database file is the source of truth

The table on screen is only a view of the data. Whenever something changes, we write to the database first, then reload the view from the database. If you ever find yourself editing the table widget directly to “update” data, stop: that way lies bugs where the screen and the database disagree.

3. Qt runs an event loop and talks with signals

app.exec() starts a loop that waits for events (clicks, key presses, timers). Widgets announce what happened with signals, and you subscribe a function (a slot) with .connect():

No polling, no while True. You describe what should happen when, Qt does the waiting.

4. Layers: each folder has exactly one job

This is the big one, and it gets its own section next.

Architecture: four layers, arrows only point down

Why bother with layers in a tiny app?

Use the replacement test. If your boss says “we are moving from desktop to a web page”, you throw away ui/ and keep everything else. If they say “we are moving from SQLite to PostgreSQL”, you rewrite db/ and keep everything else. If a change in one place forces edits in three folders, the structure is wrong. Habits formed on a 500-line app are the ones that survive on a 500,000-line one.

What is __init__.py for?

A folder containing an __init__.py is a Python package, which is what lets you write from db.task_repo import create. It also solves a git quirk: git does not track empty folders, so a one-line (even empty) file keeps the folder in your repository.

2

Config, connection and schema

About 30 minutes · Goal: running init_db() creates a todo.db file with a tasks table.

Why

The database layer needs three small things before any real query: constants (where is the file?), a safe way to open a connection (commit when it worked, roll back when it didn't, always close), and the table definition. Doing the connection handling once, in one place, means no other file can forget it.

2.1 config.py: constants in one place

  • Path(__file__).resolve().parent is “the folder this file lives in”. Using it means todo.db is created next to the code no matter which folder you launch from.
  • STATUSES is the single source of truth: the dialog's drop-down, the validation and the filter will all read this list. Add a status here and the whole app learns it.
  • PRIORITIES maps a number to a label. We store the number because ORDER BY priority then puts High (1) first for free.

2.2 db/connection.py: open, commit, roll back, close

  • sqlite3.connect(path) opens the file, or creates it if it is missing.
  • row_factory = sqlite3.Row lets us write row["title"] instead of remembering that title is column number 1.
  • @contextmanager turns the function into something you can use with with. Everything before yield is set-up, the value after yield is handed to the with block, and everything after is clean-up.
  • If the block finishes normally: commit() (make changes permanent). If it raises: rollback() (undo half-finished work) and re-raise so the caller still knows. Either way finally closes the connection.
  • db_path or config.DB_PATH reads config.DB_PATH at call time, not at import time. Remember this: it is what lets our tests in step 13 point the app at a throw-away database.
Why open and close for every operation?

SQLite connections are cheap, and a short-lived connection cannot go stale, leak, or be used from the wrong thread. It is the simplest correct design for a desktop app of this size. (Connection pooling is something you learn when you actually have a performance problem.)

2.3 db/schema.py: the table

  • IF NOT EXISTS makes init_db() idempotent: safe to call on every start-up.
  • INTEGER PRIMARY KEY AUTOINCREMENT: SQLite hands out ids 1, 2, 3… and never reuses a deleted one.
  • NOT NULL DEFAULT ...: the database itself refuses a missing title and fills sensible defaults. This is your last line of defence behind the Python validation.
  • due_date is nullable TEXT: SQLite has no date type, so we store ISO strings (2026-12-31), which conveniently sort in date order.
  • CURRENT_TIMESTAMP is filled in by the database (in UTC) when a row is inserted.

The Task model and validation

About 25 minutes · Goal: a Task object that knows what “valid” means.

Why

Passing around loose tuples like (1, "Buy milk", "Todo", 2, None) is how bugs are born: nobody remembers what position 3 is. A Task object has named fields. And the rules for what is valid belong with the data, not inside a button handler, so the dialog, the tests and any future import script can all reuse them.

  • @dataclass writes __init__, __repr__ and __eq__ for you from the annotated fields.
  • Fields without defaults (title) must come before fields with defaults. That is a Python rule.
  • id is None until the task has been saved, which is how we tell “new” from “existing”.
  • validate() returns a list of messages and never raises. Errors as data means the UI can show all the problems at once instead of one per click.
  • It reads config.STATUSES and config.PRIORITIES, so the rules stay in sync with the drop-downs automatically.
  • date.fromisoformat raises ValueError for anything that is not a real date, so 31/12/2026 and 2026-13-40 are both caught.
Run and verify
Common mistakes
  • TypeError: non-default argument 'id' follows default argument: you put a defaulted field above one without a default.
  • Using a mutable default like tags: list = []. (Not needed here, but remember: dataclasses require field(default_factory=list) for that.)
  • Importing PyQt6 in this file. The model must not know a UI exists.

Repository: Create and Read

About 35 minutes · Goal: save a Task to the database and get it back.

Why a “repository”?

A repository is a module whose only job is translating between Task objects and database rows. Everything above it speaks Task; only this file speaks SQL. That is the replacement test from the architecture section in action.

Write the first half of the file now. (We will add to it in the next step.)

The most important rule in this whole project

Values go into SQL through ? placeholders, never by gluing strings together:

If a user types x'); DROP TABLE tasks; -- as a title, the first version runs that as SQL and deletes your table. The second treats it as plain text. (In step 13 you will write a test that proves it.)

  • _row_to_task is the only place that knows column names map to Task fields. The leading underscore means “private to this file”.
  • cur.lastrowid is the id SQLite just generated, which is useful to return.
  • return cur.lastrowid sits inside the with block, and the commit still happens. The return simply runs the context manager's after-yield code first.
  • The tuple (task_id,) needs that trailing comma. (task_id) is just a number in brackets, and SQLite would complain about the wrong number of bindings.
  • fetchone() returns None when nothing matches, so get_by_id returns None for a missing id and the caller decides what to do.

Run it twice and the first number becomes 2 and the last 2: the data persisted in todo.db. Delete todo.db now so the next step starts with a clean slate. It is only a file, and init_db() will recreate it.

Common mistakes
  • sqlite3.ProgrammingError: Incorrect number of bindings supplied: count your ? against the tuple, and check for the trailing comma.
  • sqlite3.OperationalError: no such table: tasks: you did not call init_db() first, or you are looking at a different todo.db because you ran from another folder.
  • Building SQL with an f-string “just this once”. There is no “just this once”.

Repository: Update, Delete, Search

About 35 minutes · Goal: finish the repository, so the entire data layer is done before any UI exists.

Why finish the data layer first?

Bugs are cheaper to find when only one layer can be at fault. If the repository is correct before the UI exists, then any later misbehaviour is a UI bug. This is called working bottom-up.

5.1 Add update and delete

Add these two functions at the bottom of db/task_repo.py:

  • UPDATE ... WHERE id = ?: never forget the WHERE. Without it every row in the table gets the same title.
  • cur.rowcount is how many rows were changed. > 0 lets the caller know whether the id actually existed.
  • update raises ValueError for a task without an id. That is a programming error (a bug), so failing loudly is right; compare with validation, which handles user mistakes.

5.2 Replace list_all with the filtering version

Delete your simple list_all and type this one instead:

  • WHERE 1 = 1 is always true. It gives every optional filter the same shape: AND ....
  • The user's text is never put into the SQL. We build a params list in the same order as the ? marks.
  • f"%{search.strip()}%" is fine: that f-string builds the value (the % wildcards belong to the value), while the SQL text stays constant.
  • ORDER BY priority ASC, due_date IS NULL, due_date ASC, id DESC: high priority first, then tasks that have a due date (soonest first) before those that do not, and newest first as a tiebreaker.

Main window shell

About 45 minutes · Goal: a window with the toolbar and an empty table. Nothing works yet, and that is fine.

Why shell first

Layout bugs and logic bugs are different animals. Build the looks first, see it on screen, then add behaviour one feature at a time. Every later step touches only a few lines.

6.1 ui/main_window.py

We import everything we will eventually need now, so we do not keep scrolling to the top. A few imports will be unused for a while, which is normal.

6.2 main.py

How the window is put together

  • QMainWindow gives us a ready-made frame: a central area, a status bar, room for menus.
  • Widgets are the visible things: QLineEdit (text box), QComboBox (drop-down), QPushButton, QTableWidget.
  • Layouts position widgets so you never compute pixel coordinates. QHBoxLayout lines things up in a row, QVBoxLayout in a column. Here a row (the top bar) sits above the table in a column.
  • stretch=1 on the search box means “take all the spare width”, so the buttons stay at their natural size.
  • A layout needs a container widget, and a QMainWindow needs one called its central widget. That is the central = QWidget() part.
  • setSelectionBehavior(SelectRows) + SingleSelection: clicking a cell selects the whole row, one at a time. NoEditTriggers stops users typing straight into cells, because all edits go through the dialog and the database.
  • setSectionResizeMode(1, Stretch): column 1 (Title) soaks up the extra width; the other columns fit their content.
  • setObjectName("primary") is a label we can target from the stylesheet in step 12. It does nothing visible yet.
  • In main.py: init_db() runs before the window exists, because the window will soon ask for data. app.exec() starts the event loop and only returns when the window closes; sys.exit(...) passes its exit code to the OS.

Create: the add-task dialog

About 60 minutes · Goal: click “+ Add task”, fill a form, see it in the table. The C in CRUD, and your first signals and slots.

Why one dialog for add and edit

Adding and editing need the same fields, same drop-downs and same validation. Two dialogs would mean two copies to keep in sync. So TaskDialog takes an optional task: None means “new”, a Task means “edit this one”. We type the edit-mode parts now so we only write this file once; they start working in step 9.

8.1 ui/task_dialog.py

How the dialog works

  • QDialog.exec() shows the dialog modally: the main window is blocked until it closes. exec() returns QDialog.DialogCode.Accepted or Rejected.
  • Signals and slots: buttons.accepted.connect(self._on_save) means “when Save is clicked, call _on_save”. rejected is wired to the built-in reject() which closes the dialog.
  • has_due_input.toggled.connect(self.due_input.setEnabled) connects a signal straight to another widget's method: ticking the box enables the date picker. No code of ours is involved.
  • addItem(label, value) + currentData(): a combo box can show “High” while storing 1 behind the scenes. findData(1) does the reverse lookup when we fill the form for editing.
  • _read_form() / _fill_form() are the two directions of travel: widgets to Task, and Task to widgets.
  • _on_save validates, and does not call accept() if there are errors. The return keeps the dialog open so the user can fix the problem without retyping.
  • self.task_result is how the dialog hands the finished Task back to the caller. (We avoid the name result because QDialog already has a method called that.)
  • The dialog never touches the database. It only produces a valid Task. The window decides what to do with it. Same layering idea, in miniature.

Update: edit a task

About 40 minutes · Goal: select a row, press Edit (or double-click), change it, save. The U in CRUD.

Why reload from the database before editing

The table on screen is a display copy: it only shows a few columns, as text. The database is the truth. So instead of trying to rebuild a Task from table cells, we only read the id from the selected row and ask the repository for the real, complete task. This also handles “someone deleted it in the meantime”.

9.1 Add three methods to MainWindow

9.2 Connect three more signals

Extend _connect_signals:

  • _selected_id() asks the table's selection model for the selected rows; it returns None when nothing is selected. Column 0 holds the id, which is why we show the ID column.
  • _update_buttons() enables Edit and Delete only when a row is selected. It runs every time the selection changes (itemSelectionChanged), including when refresh() clears the table.
  • Signals carry data. doubleClicked sends the index of the clicked cell, and edit_task takes no parameters. PyQt quietly drops any arguments the slot cannot accept, so connecting the bare method just works. Search box and status filter

About 15 minutes · Goal: the table narrows as you type or pick a status. Two lines of code, because the groundwork is already done.

Why this is so short

The repository already filters (step 5), and refresh() already reads the search box and the drop-down (step 7). The only missing piece is “call refresh() when either changes”. That is what good layering buys you: a feature that costs two lines.

  • textChanged fires on every keystroke and sends the new text. currentIndexChanged fires when the drop-down changes and sends the new index. refresh takes no parameters, so PyQt drops the extra value, and refresh re-reads the widgets itself.
  • Gotcha: if you ever give a slot an optional parameter, like def refresh(self, force=False), PyQt will pass the signal's value into it. The search text would land in force. That is one more reason refresh() takes nothing.
  • Both filters combine, because list_all(search, status) adds AND clauses.
  • Reloading on every keystroke is perfectly fine for thousands of rows. For a huge table you would add a short delay (“debounce”); see the stretch goals.
Run and verify

  4. Search for '; DROP TABLE tasks; --. Nothing bad happens, the list is simply empty.
Common mistakes
  • Writing connect(self.refresh()) with brackets: it runs once at start-up and connects nothing.
  • Filtering the table widget (hiding rows) instead of re-querying. It appears to work until you add pagination or a large dataset. Filter in SQL.

Replace your main.py with this version:

  • QSS (Qt Style Sheets) is deliberately close to CSS: selectors, braces, property: value;.
  • QPushButton#primary targets the button whose objectName is primary: the label we set back in step 6. That is the payoff for that unexplained setObjectName line.

A debugging routine that always works

  1. Reproduce it the same way twice.
  2. Read the last line of the error, then the nearest line number in your own file.
  3. Shrink the problem: can you reproduce it with a one-line python -c against the repository, with no window at all?
  4. Print the values (print(repr(x))), do not assume them. Then delete the prints.
  5. Change one thing at a time, and run again.
